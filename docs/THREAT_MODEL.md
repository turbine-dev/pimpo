# Threat model

Pimpo acts for people: it reads their email, sends messages and changes things. This page says what it defends against, how, and what it does not promise. Each defense has a test that fails if it breaks.

## Assets

- Accounts: email, calendar, chats, services with their tokens.
- The house's data: memory, receipts, routines.
- The owner's intent: rules, approvals and budget.

## Attackers

| Attacker | Can |
|---|---|
| A stranger who writes to you | put text in an email, page, calendar invite or photo that Pimpo reads |
| A malicious routine or connector author | publish to the gallery, or offer a connector |
| Someone on your network | reach ports on your machine |
| Someone at an unlocked computer | The desktop app opens as the administrator without asking. When the owner turns on the lock, the window and the floating Pimpo stay hidden until Touch ID, the account password or Windows Hello confirms, at start and after five minutes closed; turning it on requires passing the check once, so nobody locks themselves out. It guards the app's window, not the data folder or a browser session. | `device_auth::tests`, manual on each system |
| Another person in the house | use Pimpo with their own role |
| A thief with your phone | open the paired app |

## Defenses

| Threat | Defense | Test |
|---|---|---|
| Prompt injection in content read | External content is data. Irreversible actions always need approval. Explorations only simulate changes. | `TestGateInjectionLeaksNoSecret` |
| Poisoned memory | Anything the agent notes is low trust and never reaches later instructions. Facts are single lines, and topics cannot write outside the memory. | `TestGatePoisonedMemoryNeverBecomesInstruction` (50 attacks) |
| A destructive request after context was lost | Rules live outside the model, and deletes go to the trash. | `TestGateTwoHundredEmails` |
| Runaway cost or loops | The budget is checked before every model call, with call limits per run. | `TestGateLoopStopsAtBudget` |
| One person running up the house's bill, or using models they were not given | Every cost is recorded for the person it was for (chats, routines, jobs, judgments and written text), and a paid call is refused before it starts when it could pass that person's own daily limit or the house's; a guest has a small limit by default. Every model call keeps to the models the house, the person and the assistant all allow, enforced where the model is called, not in the interface: the automatic choice and fallbacks stay inside, and a model chosen by hand outside is refused. Only the owner sets these; the owner sees whether a person reached their limit, never how much they spent, and each person sees their own spending. | `TestAPersonsLimitBlocksOnlyThem`, `TestGuestsHaveASmallLimitOfTheirOwn`, `TestAllowedModelsAreTheIntersection`, `TestAutomaticChoiceStaysInsideTheAllowed`, `TestAnExplicitModelOutsideIsRefused`, `TestEachPersonHasTheirOwnLimit`, `TestJudgmentsAreThePersons` |
| Sites the agent drives (`browser.*`) | Off until the owner turns it on; Pimpo's own Chrome profile with Chrome's sandbox kept on; every request the page makes (redirects, images, scripts, fetches, form posts) is checked before Chrome sends it and refused off the hosts the run opened within its scope or on this computer or a private network, WebSockets and WebRTC are removed, and the page reached is checked again; pressing a button is irreversible and asks first; passwords are never typed; page text returned as the site's words ([RFC 0002](rfcs/0002-browser.md)). | `TestBrowseFillAndSubmit`, `TestBrowserOnlyWhenTurnedOnAndOnlyWhereAllowed`, `TestRequestsOutsideScopeNeverLeave`, `TestBrowserRefusesPrivateAddresses`, `TestBrowserOpenAddsNoHostFromABadAddress` |
| Reading the web for a routine (`web.read`, `http.getJSON`, `rss.read`, one-click unsubscribe) | The scope is the host Go really connects to (URLs with a user name are refused); every read and redirect stays on that host; connections to this computer, private networks, CGNAT/Tailscale and IPv6 forms that embed them are refused when dialling; an unsubscribe link follows no redirect. | `TestHostIsWhereGoConnects`, `TestBlocked`, `TestGetJSONWithinScope`, `TestPrivateAddressesAreRefused`, `TestRSSAndAtom`, `TestOneClickUnsubscribeStaysOffPrivateAddresses` |
| iMessage and the unofficial WhatsApp | Both answer only the paired owner. iMessage reads Messages' database read-only, only iMessages (never SMS, whose sender is easy to fake) that arrive after it starts, and sends with the text as an argument, never inside the script. The unofficial WhatsApp starts only when the owner chose it in Labs and never approves: numbered answers are ignored and notices say to choose elsewhere. | `TestIMessageHandsOverNewMessagesOnly`, `TestUnofficialWhatsAppNeverApproves`, `TestUnofficialWhatsAppWaitsForLabs` |
| Long jobs | A job runs only after the owner sees the plan and starts it, within a budget the owner sets (at most $20) and the day's limit. Each part is an exploration limited to the capabilities the plan gave it (unknown ones are dropped, none means none), so it reads for real and writes only as proposals. The parts' results reach the report as data. | `TestJobPlansRunsPartsAndReports`, `TestJobStopsAtItsBudget`, `TestJobResumesAfterARestart` |
| Voice conversation | The microphone is open only while the owner has the conversation on, and speech is transcribed on the owner's Pimpo (Whisper), never by the browser's cloud recognition. A spoken answer is a new message and never an approval: proposed actions wait for a tap, so someone talking near the device, or audio played to it, cannot approve anything. | `ui/src/test/conversation.test.ts` |
| The phone as a node | Each paired phone reports only what it shares, chosen on the phone itself; a report from a phone that does not share it is refused. Automations use a separate key that can report events and nothing else, and each phone's key and login are revoked with the phone. Positions are compared with the owner's places and dropped; photos stay on the computer and their text reaches routines as data, never as instructions. | `TestPhoneArrivingHomeAndAPhotoOfABill` |
| Learned preferences | Learned only from the owner's own requests and decisions, never from content the agent read (nor from suggestions, whose titles come from email metadata); shown to the agent as learned and not confirmed, so they shape answers but never pass a rule or approve an action; the owner confirms or removes each, and a removed one is never learned again. | `TestLearnsOnlyFromTheOwnersOwnWords` |
| Code the agent runs (`code.run`) | Off until the owner turns it on; a fresh Docker container per call with no network, a read-only root, all Linux capabilities dropped, no-new-privileges, an unprivileged user, no environment, and limits on time, memory, CPU, processes and output, from official images pinned by digest ([RFC 0001](rfcs/0001-code-sandbox.md)). | `TestEveryRunIsIsolated`, `TestImagesArePinnedByDigest`, `TestCodeRunsOnlyWhenTurnedOn`, `TestLive` (with Docker) |
| A malicious skill (SKILL.md) | A skill is third-party text the agent loads as reference, never as the owner's words; once loaded, the rest of that exploration reaches only the capabilities the owner granted it (none means none), its scripts are never run, the protection list refuses known ones by hash (at preview and again every time one is loaded), and a skill changed on disk stops working. | `TestInstallASkill`, `TestProtectionListRefusesASkill` |
| A crafted email subject steering suggestions | Suggestions see metadata only, told it is data; they never act: accepting one shows the request and starts an ordinary exploration, which simulates changes. Each round is capped at $0.02 within the daily limit. | `TestSuggestionsFromMetadataOnly` |
| Leaking secrets | Secrets sit in an encrypted vault whose key is in the OS keychain. Models see capabilities, never credentials. Backups are sealed as a whole with a passphrase of 12+ characters (scrypt N=2^17); staged imports keep their secrets encrypted with the vault key until they are in the vault. A vault key that cannot be read is an error, never replaced by a new one over existing secrets. | `TestExportImportRoundTrip`, `TestStagedImportKeepsSecretsUntilTheyAreInTheVault`, `TestOSKeyOnlyCreatesForAnEmptyVault`, `TestFileKeyIsNeverReplaced` |
| A routine doing more than it says | The runtime exposes only declared capabilities. The gallery signs content and audits each routine with every capability reachable. A routine that sends to other people, or reads the owner's data and can reach an outside host, is flagged and installs only after the owner confirms. The index is fetched over https only, and its list of authors (their ids, names and keys) must be signed by a gallery root key built into Pimpo, so whoever serves the index cannot add an author or swap one's key; an index without that signature is refused whole. The first key seen for each author is also remembered, and later installs and updates must be signed with it, by the same author, and never go back to an older version. | `TestAuditFindsUndeclaredCalls`, `TestTamperingIsCaught`, `TestAuthorsMustBeSignedByARootKey`, `TestGalleryRefusesUnsignedAuthors`, `TestGallerySignAuthors`, `TestGalleryInstallAndPublish`, `TestGalleryUpdateKeepsTheOwnersSettings`, `TestPlainHTTPIndexIsRefused` |
| A changed release or update | Each release's `checksums.txt` is signed with the release key (`checksums.txt.sig`); `pimpo update` checks the signature against the release public keys built into the binary before trusting any checksum, and refuses to install when the signature is missing or does not match. `scripts/install.sh` does the same when its `openssl` can verify Ed25519 (OpenSSL 3), and otherwise warns and checks the checksum only. The desktop app's updates are signed with their own key (Tauri). Limit: the first install trusts wherever it was downloaded from. | `TestUpdateNeedsSignedChecksums`, `TestUpdateAndRollBack`, `TestReleaseSign` |
| A connector doing more than it says | It runs as a separate process with a clean environment, exactly its declared tools, timeouts, and risk-based rules. An uploaded connector cannot take the name of one of Pimpo's own families (gmail, notify, web...). | `TestConnectorsAreHeldToTheirManifest`, `TestInstallJSONConnector` |
| Known exfiltration endpoints and patterns | A signed protection list is checked before every action, including other agents' actions through the Guard. Pimpo cannot undo other agents' actions, so through the Guard their writes (unless inside folders a rule allows), tools it cannot sort (names are normalized first; look-alike letters are not sorted) and the first visit to a new web host ask. | `TestGuardBlocksListedThings`, `TestGuardForOtherAgents` |
| Another person in the house | Every device and session belongs to one person and every request acts only for them; every route has an access rule and routes without one are the owner's. Routines, conversations, memory, activity, approvals, recordings, jobs and phone reports belong to their person, and nobody, the owner included, reads another's through Pimpo. Others' events reach the live stream only as a type. Guests' changes wait for their responsible person; a member answers only for themselves and the owner cannot answer a member's own approvals. A guest keeps facts only for themselves; a member's house facts are shown to agents as that member's words, never the owner's, and are limited in number. Memory tidying, restoring a memory version, usage reports, suggestion rounds and queued emails each act only on one person's own things, and a queued email leaves from the account of whoever queued it. Once a member has signed in, only they change their mail and calendar. Removing someone deletes their accounts, memory, chats, explorations, routines, jobs, reminders and queued emails, and their id is never given to anyone again; role changes are recorded where the person sees them. Passkeys (WebAuthn) sign each person in as themselves; Pimpo keeps only public keys, checks the signature and the address the passkey belongs to, and a passkey of someone removed opens nothing; a passkey whose signature count goes backwards (a copy) is refused and the person is told, and removing a passkey signs out its sessions. A link the owner makes for someone else is an invite: it opens nothing by itself, works once within 15 minutes and opens a session with a token of its own, which the person sees in their account and activity and can sign out; each person lists and signs out their own devices and sessions, and nobody else's. Devices unused for 180 days and passkey sessions unused for 30 are signed out, phone reports included, and repeated wrong sign-ins and passkey sign-ins started from one address are slowed and refused (requests without a credential do not count). Limit: the owner can still open an invite before the person does; the person then sees a device they did not add. Limit: whoever administers the computer Pimpo runs on can read its files; the privacy is enforced by Pimpo, not by encryption between people. | `TestGateFamilyIsolation`, `TestEveryRouteHasAnAccessRule`, `TestNobodySeesAnotherPersonsThings`, `TestMembersCannotAdministerTheHouse`, `TestPasskeySignsInAsItsPerson`, `TestIdleDevicesAreSignedOut`, `TestWrongSignInsAreLimited`, `TestAnInviteWorksOnceForItsPerson`, `TestAnUnusedInviteExpires`, `TestPeopleSeeAndRevokeTheirOwnDevices`, `TestRemovingAPasskeySignsOutItsSessions`, `TestACopiedPasskeyDoesNotSignIn`, `TestPasskeySignInsAreLimited`, `TestIdlePhonesCannotReport`, `TestSharedFactsAreTheirAuthors`, `TestOrganizeIsPerPerson`, `TestRestoreForLeavesOthersFactsAlone`, `TestReportIsOnlyTheirsOwn`, `TestSuggestionsSeeOnlyTheOwnersRoutines`, `TestSendsAsWhoeverQueued`, `TestOnlyTheResponsibleAnswers`, `TestOnlyGuestsHaveAResponsible`, `TestIDsAreNeverReused`, `TestRemovingSomeoneDeletesTheirThings`, `TestTheOwnerCannotReplaceASignedInMembersAccounts`, `TestRoleChangesAreShownToThePerson` |
| Messages to third parties and physical actions | `whatsapp.send_to` and `ha.critical` always ask, whatever the rules say. | `TestWhatsAppToOthersAlwaysAsks` |
| Network exposure | The server listens on loopback. Home mode listens only on a private address (never a public one) and is off by default. Remote access uses the Tailscale built into Pimpo: Funnel ends TLS on this machine, so Tailscale never sees the traffic in the clear. Every way in needs a per-device token that can be revoked; the owner's login link is printed only when made and `pimpo token rotate` replaces it. A browser's cookie changes nothing unless the request comes from Pimpo's own page (Origin or Sec-Fetch-Site must match), so another page, such as one on another port of this computer, cannot act through it; JSON bodies must be declared as JSON. Every answer forbids framing and allows only Pimpo's own scripts (Content-Security-Policy). | `TestDevicePairingAndRevocation`, `TestLANUsesOnlyHomeAddresses`, `TestPhoneLinksWithTailscaleAndHome`, `TestCrossOriginWritesAreRefused`, `TestPhoneReportsNeedPimposOwnPage`, `TestSecurityHeaders`, `TestSetToken` |
| Backups in someone else's storage | Every export, cloud or not, is encrypted and authenticated as a whole on this machine (scrypt + AES-GCM, with a SHA-256 manifest of every file), so S3 or Google cannot read or change the database, memory, connectors or secrets; import and cloud restore refuse a file that is not sealed. S3 endpoints must use https (except on loopback) and bucket names are checked. Google Drive access is limited to files Pimpo created (`drive.file`). Storage keys and the passphrase stay in the vault and are never sent back to the interface. Retention deletes only files named like Pimpo backups. | `TestTamperedBackupsAreRefused`, `TestCloudBackupsToS3`, `TestS3SignsEveryRequest`, `TestS3RefusesPlainHTTPAndOddBuckets` |
| A third-party MCP server | Only the owner can add one. Pimpo lists its tools and the owner sets each tool's risk; every tool starts as irreversible and asks first, and the server's own hints are shown only as its claim. Packages are pinned to a version, local servers get a clean environment with only the variables given, remote servers need https (plain http only on this computer, judged by the exact host) and are never followed to another host, and keys live in the vault. Tools added later stay hidden; a tool that vanishes, or whose description or parameters change, blocks the connector until it is reviewed again. | `TestAddMCPServerFromTheRegistry`, `TestImportedRemoteConnector`, `TestProbeReportsTheServersClaims`, `TestChangedToolIsStopped`, `TestRemoteURLNeedsHTTPSOrThisComputer`, `TestRemoteServerRedirectKeepsTheKeyHome` |
| A chat talked into acting | Chat messages run as explorations: reads are real, changes are simulated and shown. Confirming performs only the recorded actions of that one answer, once, through the policy and approvals like a routine; the agent cannot add actions at confirm time. A conversation is visible only to the person who started it, and searching conversations looks only in the caller's own. | `TestChatRehearsesThenDoesExactlyWhatItShowed`, `TestSearchingConversations` |
| An assistant stepping outside its role | An assistant's tools are a list the host enforces: it is shown only those tools and any other call is blocked and recorded. Its instructions go to the agent as a job description, never as a way around rules. Only the owner creates assistants. | `TestAssistantOnlyUsesItsCapabilities` |
| Someone else messaging the Discord, Slack, Signal, Telegram or WhatsApp bot | A channel answers only the account that paired with a pairing code: the owner's (10 characters, valid 15 minutes, used once on one channel) or an invite (10 characters, valid 24 hours, used once). Wrong codes get no answer; a sender with 3 wrong codes is ignored for an hour, and 10 wrong codes from anyone change the owner's code. Telegram pairs and listens only in private chats. Numbered answers resolve only the choices of the latest notice to the owner, once, within 10 minutes, unless they reply to an older notice (Discord, Slack, Signal), which answers exactly that one, once, and a reply naming a message Pimpo does not have answers nothing; a number sent just as a newer notice arrived shows its choices again, and "always" (a lasting rule) is never offered by number. Notices for other people never reach these channels. | `TestSignalLikeChannelPairsAndAnswersByNumber`, `TestLinkPairingGivesGuessersNothing`, `TestWhatsAppPairingGivesGuessersNothing`, `TestPairingCodeResistsGuessing`, `TestGroupsAndChannelsAreNeverAWayIn`, `TestInvitesExpireAndRenew`, `TestNumberedAnswersAreBoundToTheLatestNotice`, `TestLinkNumbersNeverMakeRules`, `TestAReplyAnswersItsNotice` |
| An email forging the owner's address | The email channel takes a message only when the receiving provider's own Authentication-Results (the top one) show DKIM or DMARC passing for the owner's domain; without that header nothing is taken. Earlier answers reach the next turn as JSON strings labelled as Pimpo's words, so quoted mail cannot pose as the owner. | `TestEmailChannelOnlyHearsTheOwner`, `TestHistoryKeepsEarlierTurnsAsData` |
| An API model running up a bill | An API model runs only with a price set by the owner; its tokens are counted into the daily budget on every turn and the loop stops at the call's cost limit. Keys stay in the vault. Its tool calls go through Pimpo's MCP server, so rules and approvals apply exactly as with Claude Code. | `TestExploreWithAnAPIModel`, `TestAnthropicAgentLoop` |
| An email that tries to steer a routine's written text | A routine's write step only returns text: the item is passed as data with a system prompt that forbids following it, the output is capped in length and recorded, and anything the routine does with it goes through the policy and approvals like any other call. Each text is checked against the budget first and a run may ask for at most 20. | `TestWriteStep`, `TestWriteIsBudgetedAndRecorded`, `TestWriteStepPrompt` |
| Text in a desktop notification | Titles and bodies (from email subjects or model output) reach the system notifier as arguments or environment variables, never inside a PowerShell or AppleScript script. The desktop app obeys `/desktop/*` only for addresses with exactly the local Pimpo's scheme, host and port. | `TestNotifyKeepsTextOutOfScripts`, `only_this_computers_pimpo_is_local` |
| Forged webhooks | WhatsApp checks Meta's signature and handles each message id once (a replayed body repeats nothing), dropping messages older than a day. The generic channel signs what it sends; it is the owner's, so it receives only the owner's notices and acts for nobody else. | `TestWhatsAppChannel`, `TestWhatsAppMessagesAreHandledOnce`, `TestGenericChannel` |
| Tampered history | Events are chained by hash; an import with a broken chain is refused. A snapshot restore keeps the current devices, passkeys, login link and people, so it does not bring back access that was revoked, and snapshots do not follow symlinks. | event store tests, `TestBrokenHistoryIsRefused`, `TestRestoreKeepsWhoMaySignIn`, `TestSnapshotsSkipSymlinks` |
| A lost phone | Revoke the device in Settings; the owner's session is unaffected. | `TestDevicePairingAndRevocation` |

## Not promised

- A compromised computer. Anyone who controls the machine Pimpo runs on controls Pimpo.
- A model's judgment. Judgments are probabilities; anything irreversible waits for a person.
- A person who approves something harmful. The receipts show it, and undo works where the service allows.
- Services' own security (Google, Meta, Telegram).
